# i18n

Three things can be localized independently: the **URL** (locale prefix), the
**chrome** (headings, buttons, category labels), and the **content** (the
markdown itself). Most help centers start with all three in one language and
add them in that order. The module treats each as its own seam so the
progression needs no rewrite.

## Strategies

| | URL | Chrome | Content | Canonical of `/pl/help/app/x` | hreflang |
|---|---|---|---|---|---|
| **A. Single language** | prefixed routes render for every locale | one language | one tree | `/help/app/x` (default locale) | none |
| **B. Localized chrome** | same | strings table per locale | one tree | `/help/app/x` — the body is still a duplicate | none |
| **C. Translated content** | same | per locale | per-locale tree with fallback | `/pl/help/app/x` if `pl/app/x.md` exists, else `/help/app/x` | only across locales that have the file |

The module is configured by two switches:

- `HELP_CONTENT.routeLocales` — which locales get routes at all.
- `HELP_CONTENT.perLocaleDirectories` — `false` for A/B, `true` for C.

Everything else — `translated` on each article, canonical/hreflang, sitemap
membership, the "not translated" notice — derives from those two and from
which files exist. See the behaviour contract in
[content-loader.md](content-loader.md) and the metadata helpers in
[routes.md](routes.md).

**Why not 404 the untranslated page?** Because navigation must stay complete.
A Polish visitor browsing `/pl/help` should see every article, read the ones
that exist in Polish, and get the English one otherwise — with a canonical that
tells search engines it is the same document. Hiding untranslated articles
makes the localized help center look empty exactly when it is new.

## Strings

Every user-facing string in the chrome is a key in one typed table. No
literals in components: the earlier implementation had "Help Center", "All
articles", "Search articles...", "Popular articles", "Updated",
"article/articles" and the category labels inline, in a site with several
locales, so `/pl/help` rendered an English header above a Polish footer.

```ts
// file: src/lib/help/strings.ts
import type { HelpCategoryId } from "./config";

/** `other` is mandatory; add `one`, `few`, `many` as the locale needs. */
export type PluralForms = Partial<Record<Intl.LDMLPluralRule, string>> & { other: string };

export type HelpStrings = {
  title: string;
  heading: string;
  tagline: string;
  searchPlaceholder: string;
  searchLabel: string;
  noResults: string;
  allArticles: string;
  breadcrumbs: string;
  openMenu: string;
  closeMenu: string;
  openSearch: string;
  featuredHeading: string;
  relatedHeading: string;
  /** `{tag}` placeholder — the tag page title. */
  tagHeading: string;
  tagsHeading: string;
  backTo: string;
  updated: string;
  articleCount: PluralForms;
  comingSoon: string;
  notTranslated: string;
  notFound: string;
  categories: Record<HelpCategoryId, { label: string; description: string }>;
};

/** `{name}` placeholders; unknown names are left in place so a typo is visible, not blank. */
export function formatMessage(template: string, values: Record<string, string | number>): string {
  return template.replace(/\{(\w+)\}/g, (match, key: string) => {
    const value = values[key];
    return value === undefined ? match : String(value);
  });
}

export function plural(locale: string, forms: PluralForms, n: number): string {
  const rule = new Intl.PluralRules(locale).select(n);
  return formatMessage(forms[rule] ?? forms.other, { n });
}

/**
 * `YYYY-MM-DD` parses as UTC midnight. Format in UTC, or every viewer west of
 * Greenwich sees the previous day.
 */
export function formatDate(locale: string, isoDate: string): string {
  return new Intl.DateTimeFormat(locale, { dateStyle: "long", timeZone: "UTC" }).format(
    new Date(isoDate),
  );
}

export const HELP_STRINGS_EN: HelpStrings = {
  title: "Help Center",
  heading: "How can we help?",
  tagline: "Guides, references, and documentation.",
  searchPlaceholder: "Search articles…",
  searchLabel: "Search articles",
  noResults: "No articles match “{query}”.",
  allArticles: "All articles",
  breadcrumbs: "Breadcrumb",
  openMenu: "Open menu",
  closeMenu: "Close menu",
  openSearch: "Search",
  featuredHeading: "Start here",
  relatedHeading: "Related articles",
  tagHeading: "Articles tagged “{tag}”",
  tagsHeading: "Browse by tag",
  backTo: "Back to {label}",
  updated: "Updated {date}",
  articleCount: { one: "{n} article", other: "{n} articles" },
  comingSoon: "Articles coming soon.",
  notTranslated: "This article has not been translated yet.",
  notFound: "Not found",
  categories: {
    app: {
      label: "Using the app",
      description: "Get started, manage services, bookings, team members, payments, and settings.",
    },
    general: {
      label: "Learn",
      description: "The concepts behind the product, explained.",
    },
    development: {
      label: "Developers",
      description: "API, authentication, webhooks, real-time subscriptions, and embedding.",
    },
  },
};

const STRINGS: Record<string, HelpStrings> = { en: HELP_STRINGS_EN };

/**
 * SEAM: return the host's translations. Falling back to English keeps a
 * missing locale from blanking the UI; validation of locale files is the
 * host's job.
 */
export function getHelpStrings(locale: string): HelpStrings {
  return STRINGS[locale] ?? HELP_STRINGS_EN;
}
```

The table is a plain object so it can cross the server → client boundary as a
prop. That is why plurals are data (`PluralForms`) rather than functions.

### Mapping to a host i18n system

| Host has | Do this in `getHelpStrings` |
|---|---|
| JSON dictionaries (`content/i18n/{locale}.json`) | `return { ...HELP_STRINGS_EN, ...dictionary.help }` — a key missing from one locale falls back to English instead of rendering `undefined`. The spread is shallow, so keep `categories` and `articleCount` complete per locale, and still add the `help` block to **every** file: a loader that falls back per *file* (the common `fs.existsSync` pattern) does not fall back per *key* |
| `next-intl` | `const t = await getTranslations({ locale, namespace: "help" })`, then build the table; keep the type |
| Nothing | Keep `HELP_STRINGS_EN`; the component code needs no change when i18n arrives |

Polish and other few/many languages: `articleCount: { one: "{n} artykuł", few: "{n} artykuły", many: "{n} artykułów", other: "{n} artykułu" }`. `Intl.PluralRules` picks the form; nothing else changes.

## Paths

```ts
// file: src/lib/help/paths.ts
import { HELP_CONTENT, type HelpCategoryId } from "./config";
import { helpPath } from "./model";

/**
 * SEAM: replace the body with the host's locale-aware path helper. The
 * default here — no prefix for the default locale, `/<locale>` otherwise — is
 * the common convention; a host that localizes slugs (`/pl/pomoc`) plugs its
 * alias map in here and nothing else changes.
 */
export function localizePath(locale: string, path: string): string {
  return locale === HELP_CONTENT.defaultLocale ? path : `/${locale}${path}`;
}

export const helpHref = {
  home: (locale: string): string => localizePath(locale, helpPath.home()),
  category: (locale: string, category: HelpCategoryId): string =>
    localizePath(locale, helpPath.category(category)),
  article: (locale: string, category: HelpCategoryId, slug: string): string =>
    localizePath(locale, helpPath.article(category, slug)),
  tag: (locale: string, slug: string): string => localizePath(locale, helpPath.tag(slug)),
};

export function absoluteUrl(path: string): string {
  return `${HELP_CONTENT.siteUrl}${path}`;
}
```

Client-safe (no `fs`), so client components import `helpHref` directly rather
than receiving link builders as props — functions cannot cross the RSC
boundary.

## Locale-sensitive behaviour, in one place

| Concern | Implementation | Where |
|---|---|---|
| Article sort | `Intl.Collator(locale)` on title — `ą` sorts after `a`, not after `z` | loader |
| Date display | `Intl.DateTimeFormat(locale, { timeZone: "UTC" })` | `formatDate` |
| Plurals | `Intl.PluralRules(locale)` | `plural` |
| Search | Diacritics folded on both sides; no stemming | [search.md](search.md) |
| Tag URLs | Same folding as search: `Płatności` → `/help/tag/platnosci` in every locale | `tagSlug` in [tags.md](tags.md) |
| Nav and search data | Built from `getHelpIndex(locale)`, so a translated title shows in the sidebar | `HelpShell` |
| `lang` attribute | The host's root layout sets `<html lang>`; an untranslated article body is in `article.locale` — set `lang={article.locale}` on the prose container when it differs | article page |

## Adding a locale

1. Add it to `HELP_CONTENT.routeLocales`.
2. Add a strings table (or the host dictionary block) for it.
3. If `perLocaleDirectories`, create `content/help/<locale>/` — empty is fine;
   every article falls back until translated.
4. Run `validate:help`; the untranslated articles are not errors.
5. Check `/<locale>/help/<category>/<slug>` shows the notice and a canonical
   pointing at the default locale.

## Checklist

- [ ] No string literal in any help component — grep for `"` inside JSX
- [ ] `getHelpStrings` wired to the host i18n, with keys in every locale file
- [ ] `localizePath` delegates to the host helper if one exists
- [ ] Dates render in the page locale; sample `/de/...` shows German month names
- [ ] Untranslated article: notice visible, canonical correct, absent from sitemap
